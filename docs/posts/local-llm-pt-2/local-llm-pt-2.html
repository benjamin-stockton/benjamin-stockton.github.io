WarningTLDR

Local models are closer to being useful that I thought. It turns out the harness, tools, and how I prompt the agent matter a lot. Local models can complete about 80% of the notebook edits I wanted, but I still needed to finish things up to get the final document. They aren’t a time-saver yet.

A few weeks ago, I tried using a local LLM on my work issued MacBook Air M2 with 24 GB RAM to reformat and modify an example of a lab session Quarto notebook for a machine learning workshop. This notebook was based on one we actually used for a workshop last month, but will never be used in an actual class setting. The reformatting is purely to see if local models are useful. In my previous post, I found that I couldn’t get the local model to do anything useful. But I decided to try again because maybe it was just a particular harness, tool, or prompt issue.

I’m trying the Heart Classification edits again using a new harness, OpenCode, the larger Gemma 26B a4b QAT model, and a new Edit tool from GitHub. This updated Edit tool that uses line numbers to read in the old lines rather than having the model hallucinate lines. That alone basically fixes 90% of what was preventing the model from doing anything before and conveniently also uses fewer tokens.

Now the model gets stuck looping through and repeating instructions to itself before correctly implementing edits, but that’s mostly a matter of being inefficient with tokens and taking too long. (At least this is all local and I’m not paying for it.) Once I get it to do a step, \compact can get rid of all of the extraneous looping and notes-to-self by the model.1

That being said, the agent still struggles with tool use because the line replacements shift line numbers so that it loses track of where the text should be before and after editing. This problem would also be a deal-breaker for any actual use as a programming tool, but it is somewhat addressable by adding the following to the AGENTS.md:

# Tools

- When using the Edit tool, remember that you must use `startLine` and `endLine` and that making multi-line edits or line deletions will change the line numbers. Be careful and double check whether line numbers have changed after making each edit by inspecting `startLine - 5` to `endLine + 5`.

- Never replace an entire file's contents.

- Ask for help if something is confusing.

and to the prompt:

... Be careful with edits and make sure to double check whether lines have changed following the edits. Be precise and only make the minimal changes necessary to achieve the goal in each step. ...

With these added instructions, Gemma 26b a4b QAT was able to nearly one-shot almost all of the edits. It completed steps 2, 3, and 4 one-at-a-time, but then upon asking it to fix a typo in code from step 4, it proceeded to one-shot the rest of the plan. I needed to do some compaction after that long interaction.

I tried to get the model to do some final clean up (code chunk labels, fixing the final graphic, removing the BART variable importance figure, etc.), but OpenCode or LM Studio cached the entire session and ate the context window. I ended up making a new session and finished the edits on my own. While the agent model made most of the edits and they were functional, actually getting a Quarto document that could render took a little more effort on my part.

Ultimately, even with the agent fulling working with updated instructions, a better LLM, and updated tool, it still took me another half hour to get a final notebook on top of an afternoon of my MacBook running the local model to do a partial edit on its own. If/when local models are good enough to run on a MacBook and complete tasks completely and accurately, this could be a very useful tool for speeding up some data science-y tasks like making performance graphics/tables and writing basic boilerplate code. Right now, it still isn’t quite there without a ton of hand-holding.

   - Define a decision tree model specification using `parsnip`.
   - Implement hyperparameter tuning (e.g., `tree_depth`, `min_n`, `cost_complexity`).
   - Evaluate performance on the test set.

4. **Random Forest Implementation**
   - Define a random forest model specification using `parsnip` and `ranger`.
   - Implement hyperparameter tuning (e.g., `mtry`, `trees`, `min_n`).
   - Evaluate performance on the test set.

5. **BART Implementation**
   - Define a BART model specification using `parsnip`.
   - Implement hyperparameter tuning (e.g., `trees`, `prior_terminal_node_coef`, `prior_terminal_node_expo`, `prior_outcome_range`).
   - Evaluate performance on the test set.

6. **XGBoost Implementation**
   - Define an XGBoost model specification using `parsnip`.
   - Implement hyperparameter tuning (e.g., `trees`, `tree_depth`, `min_n`, `loss_reduction`, `sample_size`, `mtry`, `learn_rate`).
   - Evaluate performance on the test set.

7. **Student Exercise: Regularized Logistic Regression**
   - Provide a code scaffold for students to:
     - Specify a logistic regression model with regularization (e.g., `glmnet`).
     - Perform hyperparameter tuning for regularization parameters.
     - Evaluate the model performance.

8. **Model Comparison and Visualization**
   - Generate a summary table of performance metrics (accuracy, sensitivity, specificity, etc.) using `kableExtra`.
   - Create visual comparisons of model performances using `ggplot2`.
